08. Deploy da aplicação Flask

Neste capítulo vamos preparar a aplicação Flask containerizada. O objetivo é entender a relação entre Deployment, Service e Route, que será usada depois na pipeline Tekton.

Fluxo: código Python Flask → imagem container → Deployment → Pod → Service → Route → usuário acessa a aplicação.

Arquivos principais

app/app.py: aplicação Flask simples.
app/requirements.txt: dependência do Flask.
app/Dockerfile: definição da imagem container.
openshift/deployment.yaml: objeto que cria a aplicação no cluster.
openshift/service.yaml: exposição interna.
openshift/route.yaml: exposição externa via OpenShift Route.

Antes dos manifestos: o que é uma imagem, e o que é YAML?

Imagem de container: é o "pacote fechado" com a aplicação Flask, o Python e as dependências já dentro, pronto para rodar. O Dockerfile é a receita que descreve como montar essa imagem; depois de construída, ela fica guardada no registry interno do OpenShift, pronta para ser usada pelo Deployment.
YAML: é o formato de texto usado para descrever, de forma declarativa, "o que eu quero que exista" no cluster — por exemplo, "quero 1 réplica desta aplicação rodando". Você não diz passo a passo como fazer; você descreve o resultado desejado, e o OpenShift se encarrega de alcançá-lo. Indentação (espaços) importa muito em YAML — é assim que ele entende a hierarquia dos campos.

Manifesto exemplo: Deployment

apiVersion: apps/v1 kind: Deployment metadata: name: flask-app spec: replicas: 1 selector: matchLabels: app: flask-app template: metadata: labels: app: flask-app spec: containers: - name: flask-app image: image-registry.openshift-image-registry.svc:5000/tekton-lab/flask-app:latest ports: - containerPort: 8080

Entendendo os campos do Deployment

replicas: 1 — quantas cópias (pods) do container o OpenShift deve manter rodando. Se o pod morrer, o Deployment cria outro automaticamente até bater esse número.
selector.matchLabels — como o Deployment "reconhece" quais pods são dele. Precisa bater exatamente com os labels definidos no template logo abaixo.
template — o "molde" do pod que será criado: define os labels, os containers, a imagem e as portas.
image — aponta para o registry interno do OpenShift (image-registry.openshift-image-registry.svc:5000), no namespace tekton-lab, com a imagem que a pipeline Tekton vai construir e publicar.
containerPort: 8080 — a porta que a aplicação Flask escuta dentro do container. É essa porta que o Service vai apontar.

Manifesto exemplo: Service

apiVersion: v1 kind: Service metadata: name: flask-app spec: selector: app: flask-app ports: - port: 8080 targetPort: 8080 type: ClusterIP
selector: app: flask-app — o Service encontra os pods certos pelo label, não pelo nome. Qualquer pod com esse label vira alvo do tráfego.
port vs targetPort — port é a porta que o próprio Service expõe dentro do cluster; targetPort é a porta real do container (bate com o containerPort do Deployment).
type: ClusterIP — só acessível dentro do cluster. Quem expõe para fora é a Route, no próximo manifesto.

Manifesto exemplo: Route

apiVersion: route.openshift.io/v1 kind: Route metadata: name: flask-app spec: to: kind: Service name: flask-app port: targetPort: 8080 tls: termination: edge
spec.to.name — o nome do Service que a Route vai expor (precisa bater com o metadata.name do Service acima).
tls.termination: edge — o tráfego HTTPS é decifrado no roteador do OpenShift (não no pod). É o tipo de terminação TLS mais comum para aplicações simples como esta.
Route é um objeto exclusivo do OpenShift — não existe no Kubernetes puro, que usa Ingress para o mesmo propósito.

Laboratório guiado

1. Aplicar o Deployment

oc apply -f openshift/deployment.yaml
✓ Comando executado no simulador.

2. Aplicar o Service

oc apply -f openshift/service.yaml
✓ Comando executado no simulador.

3. Aplicar a Route

oc apply -f openshift/route.yaml
✓ Comando executado no simulador.

4. Confirmar que tudo subiu

oc get deployment,svc,route,pods
✓ Comando executado no simulador.

Troubleshooting rápido

ImagePullBackOff: imagem não existe no registry ou tag incorreta.
CrashLoopBackOff: aplicação inicia e cai; validar logs.
Route sem resposta: validar Service, porta e selector.
