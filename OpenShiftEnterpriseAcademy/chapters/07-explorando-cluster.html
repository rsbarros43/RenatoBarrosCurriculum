07. Explorando o cluster OpenShift

Agora que o projeto existe, o próximo passo é entender como observar o cluster. Um bom profissional OpenShift precisa saber navegar por nodes, pods, deployments, services, routes, events e objetos de configuração.

Fundamento: OpenShift adiciona experiência enterprise ao Kubernetes com Router, Console Web, Operators, SCC, Registry interno e comandos oc.

Mapa mental do cluster

Node: máquina onde os workloads executam. No CRC, normalmente é um nó único.
Pod: menor unidade executável, contendo um ou mais containers.
Deployment: controla rollout, réplica e atualização da aplicação.
Service: cria acesso interno estável para pods.
Route: expõe a aplicação para acesso externo no OpenShift.
ConfigMap: armazena configuração não-sensível (variáveis de ambiente, arquivos de config) desacoplada da imagem do container.
Secret: igual ao ConfigMap, mas para dados sensíveis (senhas, tokens, certificados) — o conteúdo fica em base64 e pode ser criptografado em repouso no etcd.
Operator: uma aplicação que administra outras aplicações. Encapsula conhecimento operacional (instalar, atualizar, fazer backup) em forma de controller — é assim que o OpenShift instala coisas como Tekton, monitoramento e bancos de dados de forma automatizada.

Tipos de Service

O Service tem três tipos principais, e escolher o certo importa na prática:

ClusterIP (padrão): expõe o serviço só dentro do cluster. É o que usamos no deploy da aplicação Flask — o Service fica interno, e quem expõe pra fora é a Route.
NodePort: abre uma porta fixa em todos os nodes do cluster, permitindo acesso externo direto sem depender de Route/Ingress. Menos comum no OpenShift, mais usado em Kubernetes puro.
LoadBalancer: pede um load balancer externo ao provedor de nuvem (AWS, Azure, GCP). Não se aplica ao CRC local, já que não há um cloud provider por trás.

Laboratório guiado

1. Verificar os nodes

oc get nodes
✓ Comando executado no simulador.

2. Verificar pods do projeto atual

oc get pods -o wide
✓ Comando executado no simulador.

3. Ver todos os recursos do projeto

oc get all
✓ Comando executado no simulador.

4. Ver eventos recentes

oc get events --sort-by=.lastTimestamp
✓ Comando executado no simulador.

5. Inspecionar o node

oc describe node crc-xxxxx-master-0
✓ Comando executado no simulador.

Resumo operacional

Para troubleshooting, pense nesta ordem: oc get para listar, oc describe para investigar, oc logs para analisar aplicação e oc events para entender falhas recentes.
